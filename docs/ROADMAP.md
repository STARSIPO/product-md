## После MVP

### Интеграция реального платёжного провайдера

Сейчас `PAYMENT_DRIVER=mock`. Порядок подключения:

1. Договор с банком (maib / Victoriabank) или платёжным шлюзом (Paynet / MIA), получение
   мерчант-идентификатора и ключей.
2. Реализация `createCheckout` и `parseWebhook` в `src/server/payments/<провайдер>.ts`.
3. Тестирование в песочнице: успех, отказ, повтор вебхука, испорченная подпись,
   таймаут.
4. Обязательная проверка `PAYMENT_WEBHOOK_SECRET` в продакшене (задача этапа 6).
5. Пилот на ограниченном круге компаний, затем общий запуск.

**Условие запуска:** активирован `BILLING_ENABLED`, то есть на площадке есть достаточное
предложение, чтобы оплата размещения была осмысленной.

### SMS-провайдер

* Драйвер `http` уже предусмотрен `src/env.ts`.
* Выбор местного агрегатора, договор, `SMS_API_KEY` и `SMS_SENDER`.
* Обязательно: запись каждой отправки в `NotificationDelivery` — SMS платные, и «дошло или
  нет» должно быть видно.
* Бюджетные ограничения: лимит отправок на пользователя в сутки, алерт при аномальном
  расходе.

**Условие:** телефонная регистрация даёт заметную долю конверсии, либо появляются жалобы
на недоставку email.

### Уведомления в Telegram

* Канал `TELEGRAM` уже перечислен в `NotificationDelivery.channel` и
  `NOTIFICATION_CHANNELS`.
* Бот, привязка `chat_id` к пользователю, шаблоны на RU/RO.
* Приоритетные события: новое предложение по заявке, новое сообщение, смена статуса
  сделки, низкий баланс.

**Условие:** пользователи просят, либо доставляемость email оказывается недостаточной.
В Молдове Telegram — распространённый рабочий канал, поэтому вероятность высокая.

### Мобильные приложения

* На MVP — адаптивный веб от 320 px и PWA-манифест.
* Нативные приложения (React Native или два нативных) — только после устойчивого
  использования с мобильных.
* Первый кандидат на нативность: push-уведомления и камера для быстрой публикации товара
  с телефона прямо со склада.

**Условие:** > 60 % трафика с мобильных **и** запрос на push-уведомления от активных
пользователей.

### Корпоративные аккаунты

* Несколько сотрудников с ролями тоньше, чем `OWNER` / `MANAGER`.
* Разделение прав: публикация, ответы на заявки, финансы, документы.
* Лимиты и бюджеты на сотрудника.
* Единый счёт и закрывающие документы.

**Условие:** появляются поставщики с несколькими закупщиками/менеджерами, которым тесно в
двухролевой модели.

### Массовая загрузка товаров

* Шаблоны CSV и XLSX с колонками под категории и атрибуты.
* Предпросмотр с валидацией построчно и понятными ошибками.
* Обновление существующих позиций по внешнему коду товара.
* Плановая синхронизация цен и остатков.

**Условие:** поставщики с каталогом от 50 позиций, которым ручное добавление физически не
подходит.

### Публичный API для крупных поставщиков

* REST с ключами на компанию, отдельные лимиты.
* Методы: список и обновление товаров, остатки и цены, входящие заявки, отправка
  предложений, статусы сделок.
* Вебхуки наружу: новая подходящая заявка, принято предложение, изменился статус сделки.
* Документация OpenAPI, песочница.

**Условие:** запрос минимум от 3–5 крупных поставщиков с собственными учётными системами.

### Логистические партнёры

* Каталог перевозчиков с зонами и тарифами.
* Оценка стоимости доставки в карточке и в предложении.
* Заказ перевозки из сделки.
* Ответственность за груз остаётся на перевозчике; площадка не становится оператором.

**Условие:** доля сделок, срывающихся из-за логистики, становится заметной по опросам и
по причинам отмен.

### Миграция на Elasticsearch / Typesense

Не раньше срабатывания хотя бы одного триггера:

| Триггер | Порог |
| --- | --- |
| Объём | > 100 000 активных объявлений |
| Задержка | p95 поиска > 300 мс при корректных индексах |
| Функциональность | Нужны точные фасетные счётчики по 10+ измерениям одновременно |
| Функциональность | Нужны правила ранжирования и синонимы, редактируемые без деплоя |
| Нагрузка | Поиск начинает мешать транзакционной нагрузке основной БД |

Порядок миграции и требование «SQL-путь остаётся рабочим» — в `docs/ARCHITECTURE.md`,
§13. Разработчик обязан по-прежнему поднимать проект без внешнего поискового сервиса.

### Оценка целесообразности эскроу

Эскроу решает главную проблему доверия в B2B: «я не знаю этого поставщика, я не хочу
платить вперёд». Но он же превращает информационную площадку в финансового посредника.

**Что потребуется:**

| Требование | Комментарий |
| --- | --- |
| Юридическая конструкция | Лицензия платёжного агента или партнёрство с лицензированным оператором |
| Регулятор | Согласование с Национальным банком Молдовы |
| Капитал | Резервы на удерживаемые средства |
| Операции | Разрешение споров, возвраты, арбитраж — это люди, а не код |
| Налоги | Последствия для обеих сторон сделки |
| Технически | Отдельный ledger удерживаемых средств, поэтапное освобождение, вся история движений |

**Признаки, что пора считать:**

* Доля сделок, срывающихся на этапе «кто платит первым», превышает 20 %.
* Есть спрос от покупателей на защиту предоплаты.
* Объём проходящих сделок делает комиссию эскроу экономически осмысленной.
* Найден лицензированный партнёр, готовый нести регуляторную часть.

**Промежуточный вариант, дешевле и быстрее:** «безопасная сделка» без движения денег —
чек-лист этапов, фиксация договорённостей, обязательные подтверждения обеих сторон и
эскалация к модератору при споре. Часть эффекта доверия достигается уже сейчас через
`Deal` + `DealEvent` + `Review`.
