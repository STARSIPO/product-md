## 1. Проблема и контекст рынка

### Как закупается HoReCa в Молдове сегодня

Ресторан, кафе, отель, пекарня, столовая или небольшой производитель закупает сырьё и
продукты по цепочке, которая почти не оцифрована:

| Канал | Как выглядит | Чем плох |
| --- | --- | --- |
| Личные контакты | Телефон знакомого фермера, «мясник, который возит уже пять лет» | Цена не проверяется рынком, нет альтернативы при срыве поставки |
| Viber / WhatsApp-группы | «Кто возит охлаждённую телятину в Кишинёв?» | Нет истории, нет сравнения, сообщение тонет за час |
| 999.md и аналогичные доски | Объявление о продаже в общем потоке с б/у мебелью | Нет B2B-полей (мин. партия, регулярность, документы ANSA), нет оптовых цен, нет заявок |
| Крупные дистрибьюторы | Каталог + менеджер | Высокий минимальный заказ, отсечены малые фермеры и малые покупатели |
| Рынки (Piața Centrală и др.) | Личный выезд закупщика | Съедает время, нет счёта-фактуры, нет регулярности |

Три следствия, которые формируют продукт:

1. **Поиск поставщика — ручная работа.** Закупщик не знает, кто ещё возит нужный товар в
   его район. Локальный фермер не знает, что в 20 км от него ресторан ищет ровно его товар.
2. **Цена непрозрачна.** Нет способа быстро сравнить трёх поставщиков по одной и той же
   позиции при одинаковом объёме и одинаковых условиях доставки.
3. **Доверие строится с нуля каждый раз.** Документы (регистрация, разрешения, ANSA,
   сертификаты происхождения) существуют в бумаге и PDF в почте, а не как проверяемый
   статус поставщика.

### Почему доска объявлений это не решает

Классифайд (999.md) работает по модели «продавец публикует — покупатель ищет». Для оптовой
продуктовой закупки этой модели мало: закупщику чаще нужно **не найти существующее
объявление, а получить условия под свой конкретный объём и график**. Товар «охлаждённая
говядина» без указания партии в 20 кг еженедельно с доставкой в Кишинёв — это не оффер,
а строчка. Поэтому Product.md добавляет обратное направление (см. раздел 4) и B2B-поля,
которых у классифайда нет by design: минимальный заказ, оптовые ступени цены
(`PriceTier`), регулярность поставки (`supplyRegularity`), зоны доставки
(`deliveryRegions`), сроки годности, условия хранения, аллергены, состав, партия.

### Локальный контекст, зашитый в продукт

| Особенность рынка | Как отражена в коде |
| --- | --- |
| Двуязычность RU/RO | `LOCALES = ['ru','ro']`, переведённые URL (`/ro/produse`), словари `src/lib/i18n/messages/{ru,ro}.ts` |
| Пишут без диакритики, вперемешку | `src/lib/normalize.ts` — свёртка диакритики, ru/ro-стемминг, Damerau-Levenshtein для опечаток |
| Валюта MDL, запятая как разделитель | `src/lib/money.ts` — целые бани, `parseAmountToBani` принимает и `95.50`, и `95,50` |
| Часовой пояс Europe/Chisinau | `APP_TIMEZONE` в `src/lib/i18n/format.ts`, `chisinauDayKey()` в `src/lib/utils.ts` |
| Юрформы SRL / SA / II / GT / PFA | `ORG_TYPES` в `src/lib/constants.ts` |
| IDNO — 13 цифр | `Company.idno` |
| Санитарный надзор ANSA | `VERIFICATION_TYPES.ANSA`, `DOCUMENT_TYPES.ANSA` |
| Районы и населённые пункты | Модели `District` (RAION / MUNICIPIU / UTA) и `Locality` (ORAS / MUNICIPIU / SAT / COMUNA) |

## 3. Двустороннее ценностное предложение

```
                        ┌─────────────────────────────┐
   ПРЕДЛОЖЕНИЕ          │        Product.md           │            СПРОС
   фермеры              │                             │            рестораны
   производители  ─────▶│  1. Витрина товаров         │◀─────      кафе, отели
   оптовики             │     (Product)               │            магазины
   импортёры            │                             │            кейтеринг
                        │  2. Заявки на закупку       │            пекарни
                   ◀────│     (PurchaseRequest)       │─────▶      столовые
                        │     + закрытые предложения  │            малые
                        │       (Offer)               │            производители
                        └─────────────────────────────┘
                                    │
                            Deal + Review + рейтинг
```

**Продавцу:** доступ к спросу, который иначе не виден, — без холодных звонков, без комиссии
со сделки, с бесплатным стартом.
**Покупателю:** конкурентные условия по своему объёму за один запрос, а не десять звонков;
проверяемые документы поставщика; всегда бесплатно.

Обе стороны заинтересованы в присутствии другой — это классический маркетплейс-эффект. При
холодном старте наполняется сначала сторона предложения (импорт категорий + бесплатное
размещение + пробный период), затем спрос привлекается тем, что заявка бесплатна и не
требует ничего, кроме описания потребности.

## 4. Ключевое отличие: заявки и закрытые предложения

Это то, чего нет у классифайда, и главная причина, по которой продукт вообще существует
отдельно от 999.md.

### Направление 1 — товары (как у всех)

Продавец публикует `Product`: «Говядина охлаждённая — 95 MDL/кг, мин. заказ 20 кг, доставка
по Кишинёву». Покупатель ищет, фильтрует, пишет.

### Направление 2 — заявки (дифференциатор)

Покупатель публикует `PurchaseRequest`: «Нужно 20 кг охлаждённой говядины еженедельно,
доставка в Кишинёв, оплата переводом, требуются документы ANSA». Поставщики отвечают
`Offer` — **закрытым коммерческим предложением**.

### Инвариант закрытости (sealed bid)

Определён прямо в схеме, `prisma/schema.prisma`:

> `/// SEALED BID. A supplier may only ever read its own offer; the buyer who owns the`
> `/// request reads all of them.`

Правила:

| Кто | Что видит |
| --- | --- |
| Поставщик-автор предложения | Только своё предложение целиком |
| Другой поставщик | **Ничего**: ни цену, ни условия, ни вложения, ни факт числа конкурентов сверх счётчика `offersCount` |
| Покупатель — владелец заявки | Все предложения по своей заявке |
| Гость / посторонняя компания | Ничего |
| Модератор / администратор | Доступ по служебной необходимости, с записью в `AuditLog` |

Технические гарантии:

* `Offer` имеет `@@unique([requestId, sellerCompanyId])` — один поставщик = одно
  предложение на заявку, нельзя «завалить» заявку демпингом с нескольких карточек.
* Нет публичного маршрута чтения предложений — только через сервис с проверкой владения.
* Инвариант закреплён тестом `tests/integration/offer-privacy.test.ts` (**в разработке** —
  файл ещё не создан, но он указан в схеме как обязательный и входит в этап 7 роадмапа).

Почему это важно бизнесу: без закрытости поставщики видят чужие цены, начинается гонка
вниз и подстройка «на цент дешевле», качественные поставщики уходят. Закрытая котировка —
это то, как реально работает B2B-закупка, и то, что невозможно сделать на доске объявлений.

## 5. Роли и матрица прав

### Модель ролей

Роль разложена на два независимых уровня — это важно и отражено в схеме:

| Уровень | Где хранится | Значения |
| --- | --- | --- |
| Платформенная роль | `User.role` | `USER` \| `MODERATOR` \| `ADMIN` (`USER_ROLES`) |
| Роль компании на рынке | `Company.isBuyer`, `Company.isSeller` | булевы флаги, могут быть оба `true` |
| Роль внутри компании | `CompanyMember.role` | `OWNER` \| `MANAGER` (`COMPANY_MEMBER_ROLES`) |

Поэтому «Покупатель + Продавец» — это не третья роль, а компания с обоими флагами. Гость —
отсутствие сессии.

### Где это проверяется

Всё в `src/server/auth/guards.ts`. Два семейства:

* `requireUser` / `requireCompany` / `requireSeller` / `requireBuyer` / `requireModerator` /
  `requireAdmin` — для страниц, делают `redirect()` или `notFound()`.
* `assertUser` / `assertCompany` / `assertSeller` / `assertBuyer` / `assertModerator` /
  `assertAdmin` — для server actions, бросают `AuthorizationError` с кодом
  `unauthorized | forbidden | notFound | companyRequired`.
* Владение: `assertOwnsProduct`, `assertOwnsRequest`, `assertDealParticipant`,
  `assertConversationParticipant`.

`requireAdmin` дополнительно требует включённый TOTP: администратор без 2FA отправляется на
страницу настройки, а не пропускается.

## 6. Основные пользовательские сценарии

### 6.1. Покупатель находит товар

1. Гость открывает `/ru/` (или `/ro/` — язык выбирается по cookie `NEXT_LOCALE`, затем по
   `Accept-Language`, см. `src/middleware.ts`).
2. Вводит запрос в поиск («карне де вита», «помидоры», с опечатками — работает
   `normalize()` + синонимы `CategorySynonym`).
3. Получает выдачу с фильтрами: категория, район/город, цена от-до, минимальный заказ,
   наличие (`IN_STOCK` / `PRE_ORDER` / `OUT_OF_STOCK`), только проверенные, есть доставка,
   регулярность поставки, атрибуты категории (`CategoryAttribute` с `isFilterable`).
4. Сортирует: `relevance | newest | price_asc | price_desc | rating | popular`
   (`PRODUCT_SORTS`), 24 карточки на страницу (`PAGE_SIZE`).
5. Открывает карточку товара: фото, цена, оптовые ступени `PriceTier` с бейджем скидки
   («−13 %», `tierDiscountPercent`), минимальный заказ, условия доставки, срок годности,
   состав, аллергены, документы поставщика (только результат проверки), рейтинг компании.
6. Нажимает «Показать контакты» → счётчик `contactsCount` +1, запись в `ProductStatDaily`.
   Гостя на этом шаге просят войти.
7. Пишет в чат (`Conversation` типа `PRODUCT`) или сразу договаривается о сделке.

### 6.2. Покупатель публикует заявку и выбирает поставщика

1. Вход → если компании нет, онбординг (`requireCompany` редиректит на `/ru/onboarding`).
2. «Создать заявку» → мастер формы:
   1. что нужно (умный подбор категории по тексту — синонимы + опечатки);
   2. количество и единица (`UNITS`: KG, T, G, L, ML, PCS, BOX, PACK, PALLET, SET);
   3. желаемая цена `desiredPriceBani` и/или предельный бюджет `maxBudgetBani`
      (необязательно);
   4. разовая или регулярная (`isRecurring` + `frequency`);
   5. дата первой поставки `firstDeliveryAt`, дедлайн приёма предложений
      `offersDeadlineAt`;
   6. адрес и населённый пункт доставки, радиус поиска поставщика `supplierRadiusKm`;
   7. требования: документы, упаковка, условия хранения, `allowPartial` (частичная
      поставка), `verifiedOnly` (только проверенные поставщики);
   8. вложения (`RequestAttachment` — ТЗ, спецификация);
   9. видимость `PUBLIC` / `PRIVATE`.
3. Публикация → статус `ACTIVE`, затем `RECEIVING_OFFERS` при первом предложении.
4. Поставщики получают уведомление о подходящей заявке (`NEW_REQUEST_MATCH`).
5. Покупатель видит счётчик `offersCount` и открывает **сравнение предложений**: таблица
   «Поставщик · Цена за единицу · Итог · Доставка · Дата поставки · Рейтинг · Документы ·
   Расстояние · Время ответа», лучшая цена подсвечена.
6. Отмечает интересные в короткий список (`SHORTLISTED`), уточняет условия в чате
   (`Conversation` типа `OFFER`).
7. «Выбрать поставщика» → подтверждение («Мы создадим сделку с {supplier} и уведомим
   остальных поставщиков об отказе») → предложение `ACCEPTED`, остальные `REJECTED`,
   заявка → `SUPPLIER_SELECTED`, создаётся `Deal`.

### 6.3. Продавец публикует объявление

1. Вход → онбординг компании → включён флаг «продаю» (`isSeller`).
2. «Добавить товар» → форма:
   1. категория (умный подбор; поля формы зависят от категории —
      `CategoryAttribute.appliesTo = PRODUCT | BOTH`, наследование `inherited`);
   2. название, описание;
   3. цена + единица (единица по умолчанию берётся из `Category.defaultUnit`);
   4. минимальный заказ, доступное количество;
   5. оптовые ступени `PriceTier` (от 100 кг — 92 MDL, от 500 кг — 88 MDL);
   6. происхождение, производитель, партия, даты производства и годности, условия
      хранения, температура, аллергены, состав, упаковка;
   7. доставка: условия, стоимость, самовывоз, регионы доставки;
   8. фото — до 10 (`MAX_PRODUCT_PHOTOS`), до 5 МБ каждое (`MAX_IMAGE_BYTES`), JPEG/PNG/WebP;
   9. привязка документов компании к товару (`ProductDocument`).
3. Сохранение черновика (`DRAFT`) или публикация.
4. Если включён флаг `REQUIRE_MODERATION` → `PENDING`, попадает в `ModerationTask`;
   модератор одобряет (`ACTIVE`), отклоняет (`REJECTED`) или запрашивает исправления
   (`CHANGES_REQUESTED` + комментарий, который видит пользователь).
5. Активное объявление ежедневно списывает тариф с баланса компании (когда включён
   `BILLING_ENABLED`). При нуле баланса — `pausedForBalance = true`, показ останавливается,
   предупреждение приходит заранее.

### 6.4. Продавец отвечает на заявку

1. Лента заявок с фильтрами по категории, району, объёму, дедлайну; сортировки
   `newest | deadline | budget_desc | offers` (`REQUEST_SORTS`).
2. Открывает заявку → видит требования, но **не видит** ни одного чужого предложения.
3. «Отправить предложение» → форма: цена за единицу, доступное количество, стоимость
   доставки, итог (считается `lineTotalBani`), срок поставки (дата или дней), способ оплаты
   (`CASH | TRANSFER | CARD | DEFERRED`), срок действия предложения `validUntil`,
   регулярность, комментарий, PDF-вложение, альтернативный товар из своего каталога.
4. На форме постоянно висит уведомление: «Предложение закрытое. Другие поставщики не увидят
   вашу цену, условия и вложения.»
5. Отправка → статус `SENT`; повторная отправка на ту же заявку запрещена
   (`@@unique([requestId, sellerCompanyId])`, ошибка `offerExists`).
6. Пока покупатель не принял решение, предложение можно обновить или отозвать
   (`WITHDRAWN`).
7. Статусы движутся: `SENT` → `VIEWED` (покупатель открыл) → `SHORTLISTED` → `ACCEPTED` /
   `REJECTED`; `EXPIRED` по `validUntil`.

### 6.5. Завершение сделки и отзыв

1. `Deal` создаётся из принятого предложения (или вручную из карточки товара) со статусом
   `AWAITING_CONFIRMATION` и уникальным номером `Deal.number`.
2. Обе стороны подтверждают (`buyerConfirmedAt`, `sellerConfirmedAt`) → `CONFIRMED`.
3. Дальше по конечному автомату `DEAL_TRANSITIONS` из `src/lib/constants.ts`:

   ```
   AWAITING_CONFIRMATION → CONFIRMED | CANCELLED
   CONFIRMED             → PREPARING | CANCELLED | DISPUTED
   PREPARING             → SHIPPED   | CANCELLED | DISPUTED
   SHIPPED               → DELIVERED | DISPUTED
   DELIVERED             → COMPLETED | DISPUTED
   DISPUTED              → CONFIRMED | CANCELLED | COMPLETED
   COMPLETED             → (терминальный)
   CANCELLED             → (терминальный)
   ```

   Карта читается и сервером, и UI, поэтому невозможный переход не пройдёт ни кнопкой, ни
   подделанным запросом (ошибка `dealTransitionInvalid`).
4. Каждый переход пишется в `DealEvent` (кто, из какого статуса, в какой, комментарий).
5. Печатная форма «Договорённость о поставке» — HTML-страница для печати в PDF браузером,
   с дисклеймером: Product.md — информационная площадка, договор заключается напрямую.
6. После `COMPLETED` обе стороны могут оставить отзыв — по одному в каждую сторону
   (`@@unique([dealId, direction])`):
   * покупатель → поставщику: качество, соответствие описанию, доставка, коммуникация,
     документы;
   * поставщик → покупателю: коммуникация, оплата, соблюдение договорённостей.
7. Отзыв обновляет `Company.ratingAvg` / `ratingCount` / `dealsCompleted`. Оценённая
   сторона может один раз ответить (`ReviewReply`).

## 8. Нефункциональные требования

### 8.1. Производительность

| Показатель | Цель |
| --- | --- |
| LCP на карточке товара и в каталоге (4G, средний Android) | ≤ 2,5 с |
| INP | ≤ 200 мс |
| CLS | ≤ 0,1 |
| TTFB серверного рендера каталога | ≤ 400 мс при прогретом кеше |
| Поисковый запрос по каталогу (БД) | ≤ 150 мс при 50 000 объявлений |
| Размер JS первой загрузки публичной страницы | ≤ 130 КБ gzip |
| Страница выдачи | 24 карточки (`PAGE_SIZE`), максимум 60 (`MAX_PAGE_SIZE`) |

Средства: серверные компоненты по умолчанию, `next/image` c AVIF/WebP
(`next.config.mjs`), денормализованные агрегаты вместо `COUNT(*)` на чтении, индексы под
каждый публичный запрос (см. `docs/DATABASE.md`).

### 8.2. Доступность — WCAG 2.1 уровень AA

* Контраст текста ≥ 4,5:1, крупного текста и элементов интерфейса ≥ 3:1. Палитра
  посчитана: `foreground` на `background` = 16,45:1, `primary` на белом = 6,54:1,
  `muted-foreground` на белом = 5,07:1 (таблица в `docs/DESIGN_SYSTEM.md`).
* Фокус виден всегда: `:focus-visible { ring-2 ring-ring ring-offset-2 }` в
  `src/app/globals.css`, `outline` никогда не убирается без замены.
* Полная работа с клавиатуры, логичный порядок табуляции, ловушки фокуса в модалках.
* Семантическая разметка, метки у всех полей, alt у изображений, aria-live для
  асинхронных состояний.
* Никогда не только цветом: статус = цвет + иконка + текст.
* Тач-цели ≥ 44×44 px.
* `prefers-reduced-motion` уважается глобально (`src/app/globals.css`).
* Минимальный размер основного текста 14 px; 13 px (`caption`) — только для подписей.

### 8.3. Безопасность

Полностью раскрыто в `docs/SECURITY.md`. Требования верхнего уровня:

* Все проверки прав — на сервере; клиентские роль/id/флаги игнорируются.
* Валидация Zod на каждой границе (env, формы, server actions, вебхуки).
* Пароли — scrypt; токены и сессии — только в виде хешей.
* Секреты только из окружения, продакшен отказывается стартовать с примерными
  `APP_SECRET` / `CRON_SECRET` (`src/env.ts`).
* Заголовки безопасности в `next.config.mjs`; CSP и HSTS — **в разработке**.
* Документы компаний — приватное хранилище + короткоживущие подписанные ссылки.
* Инвариант закрытых предложений — требование безопасности, а не UX.

### 8.4. Интернационализация RU / RO

* Две локали, RU по умолчанию (`DEFAULT_LOCALE`).
* Переведены не только строки, но и URL: `/ru/products` ↔ `/ro/produse`,
  `/ru/requests` ↔ `/ro/cereri` (карта `ROUTE_SEGMENTS`, 30+ сегментов).
* Словарь типизирован: `ro.ts` типизирован как `Dictionary` от `ru.ts`, поэтому
  недостающий или переименованный ключ — ошибка компиляции, а не пустая подпись в проде.
* Даты, числа, деньги — через `Intl` с тегами `ru-MD` / `ro-MD`, часовой пояс всегда
  `Europe/Chisinau`.
* Деньги форматируются с неразрывным пробелом: `95,50 MDL`.
* Переключатель языка сохраняет текущую страницу (`switchLocalePath`).
* Локализованные названия и slug'и категорий (`CategoryTranslation`).

### 8.5. SEO

* Публичные страницы (главная, каталог, категория, товар, поставщики, компания, заявки) —
  серверный рендер, индексируемый HTML.
* Отдельный URL на каждый язык + `hreflang` между `ru` и `ro` версиями.
* `title` / `description` из словаря (секция `seo`) с подстановкой названия и цены.
* Разметка Schema.org: `Product`, `Offer`, `Organization`, `BreadcrumbList` — **в разработке**.
* `sitemap.xml` и `robots.txt` (middleware их пропускает без локализации) — **в разработке**.
* Человекочитаемые slug'и с транслитерацией кириллицы (`slugify`).
* Канонические URL, чтобы фильтры не плодили дубликаты.

## 9. Бизнес-модель и тарифы

### Принципы

1. **Площадка не берёт комиссию со сделки и не принимает оплату за товар.** Покупатель и
   поставщик рассчитываются напрямую. Это зафиксировано в дисклеймере сделки и в FAQ
   тарифов.
2. **На старте всё бесплатно.** Флаг `BILLING_ENABLED` по умолчанию `false`
   (`DEFAULT_FEATURE_FLAGS`) — платная модель включается администратором, когда наберётся
   критическая масса предложения.
3. **Заявки покупателей бесплатны всегда.** Спрос — дефицитная сторона рынка, её нельзя
   облагать.
4. **Нет ежедневного списания с карты.** Компания пополняет внутренний баланс, ежедневный
   тариф списывается с него. Одна банковская транзакция на много дней.

### Тарифы

Значения по умолчанию — `DEFAULT_TARIFFS` в `src/lib/constants.ts`; администратор может
переопределить любой в рантайме через модель `Tariff`.

| Ключ | Что это | Цена | Единица |
| --- | --- | ---: | --- |
| `LISTING_DAILY` | Активное объявление продавца | **1,00 MDL** (100 бани) | за день |
| `PROMO_BUMP` | Поднятие объявления | 5,00 MDL (500 бани) | за раз |
| `PROMO_PIN_CATEGORY` | Закрепление в категории | 15,00 MDL (1500 бани) | за день |
| `PROMO_HOMEPAGE` | Размещение на главной | 30,00 MDL (3000 бани) | за день |
| `PROMO_HIGHLIGHT` | Выделение объявления | 8,00 MDL (800 бани) | за день |
| `PROMO_URGENT` | Метка «Срочно» | 6,00 MDL (600 бани) | за день |
| `PROMO_NEWSLETTER` | Продвижение в рассылке | 50,00 MDL (5000 бани) | за раз |
| Заявка покупателя | Публикация и получение предложений | **0 MDL** | — |

Базовая дневная ставка дополнительно задаётся переменной окружения
`LISTING_DAILY_PRICE_BANI` (по умолчанию `100`).

### Пополнение баланса

Пресеты из `TOP_UP_PRESETS_BANI` — подобраны так, чтобы читались как «на N дней» при
ставке 1 MDL/день:

| Пресет | Бани | MDL | Хватит примерно на |
| --- | ---: | ---: | --- |
| 1 | 3 000 | 30 | 30 дней одного объявления |
| 2 | 9 000 | 90 | 90 дней |
| 3 | 18 000 | 180 | 180 дней |
| 4 | 36 500 | 365 | год |
| Произвольная | любая | любая | считается на лету |

### Пробный период и мягкая посадка

* Новый продавец получает `SELLER_TRIAL_DAYS` дней бесплатного размещения (по умолчанию
  **30**), дата окончания — `Company.trialEndsAt`.
* При балансе ниже `LOW_BALANCE_THRESHOLD_BANI` (по умолчанию **1000 бани = 10 MDL**)
  приходит предупреждение `LOW_BALANCE`: «Баланса хватит примерно на {days} дн.»
* При нуле объявления **приостанавливаются, а не удаляются**: `pausedForBalance = true`.
  Заявки покупателя продолжают работать. После пополнения показ возобновляется.

### Дополнительная монетизация

Всё перечисленное — за feature-флагами, любой пункт выключается администратором без
деплоя (`PROMOTIONS_ENABLED`, `BILLING_ENABLED`).

| Продукт | Модель | Статус |
| --- | --- | --- |
| Поднятие, закрепление в категории, главная, выделение, «Срочно», рассылка | `Promotion` + `Tariff` | ✅ модель, 🟡 покупка |
| Расширенная аналитика продавца | подписка / включение флагом | 🟡 |
| Корпоративный аккаунт (несколько менеджеров, лимиты) | подписка | ⬜ |
| Массовая загрузка товаров (CSV/XLSX) | тариф за позицию или подписка | ⬜ |
| Платная расширенная верификация | разовый платёж | ⬜ |
| API для крупных поставщиков | подписка | ⬜ |

## 11. Явно вне MVP

Ниже — то, что осознанно **не** делается на первом этапе. Список так же важен, как список
функций: он защищает от расползания.

| Не делаем | Почему | Что вместо |
| --- | --- | --- |
| **Эскроу / удержание средств** | Требует лицензии платёжного агента, резервов и юридической конструкции; убивает срок запуска | Прямые расчёты, печатная форма договорённости, рейтинг и отзывы как механизм доверия |
| **Оплата товаров через площадку** | То же + налоговые последствия для обеих сторон | Способ оплаты фиксируется в сделке (`CASH / TRANSFER / CARD / DEFERRED`), деньги идут мимо площадки |
| **Логистика, курьеры, расчёт маршрутов** | Отдельный бизнес с отдельной операционкой | Поля условий доставки, зон доставки, самовывоза; партнёрство с перевозчиками — после MVP |
| **Elasticsearch / Typesense** | При объёмах десятков тысяч объявлений PostgreSQL с нормализованной колонкой и GIN/pg_trgm справляется; лишний сервис в инфраструктуре | SQL-поиск за интерфейсом адаптера; условия миграции описаны в `docs/ROADMAP.md` |
| Мобильные приложения (iOS/Android) | Стоимость и скорость итераций | Адаптивный веб от 320 px, PWA-манифест |
| Реальный платёжный провайдер на старте | Биллинг выключен флагом, ключей ещё нет | `PAYMENT_DRIVER=mock` воспроизводит редирект и вебхук локально |
| SMS через реального провайдера | Стоимость на этапе отсутствия трафика | `SMS_DRIVER=mock` печатает код в лог сервера |
| Telegram-уведомления | Канал уже заложен в `NotificationDelivery.channel` | In-app + email на MVP |
| Публичный API | Нужен только крупным поставщикам, которых на старте нет | После MVP |
| Массовая загрузка товаров | Требует шаблонов и валидации импорта | Ручное добавление; для крупных — помощь оператора |
| Мультивалютность | Рынок работает в MDL | Поле `currency` есть в моделях и по умолчанию `MDL` — расширяемо |
| Аукцион с открытыми ставками | Прямо противоречит инварианту закрытых предложений | Закрытая котировка + короткий список |
| Автоматический матчинг «заявка ↔ товар» с ML | Нет данных для обучения на старте | Уведомления `NEW_REQUEST_MATCH` / `NEW_PRODUCT_MATCH` по категории, району и сохранённым поискам |
